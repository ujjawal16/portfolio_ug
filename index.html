Multi-tenant Job Orchestration Platform

Enterprise AI SaaS · Co-designed with the lead engineer · Guided 2 engineers

The problem

Batch jobs ran as raw notebooks spread across teams. They were hard to maintain, expensive to run, and followed no shared standard.

What was built

An event-driven job platform on Prefect and Kubernetes (AWS EKS). Queued jobs feed ~200 parameterized deployments; each run gets its own short-lived pod with per-customer concurrency limits and automatic retries. Job logic is separated from orchestration, and the orchestrator ships as an installable Python package.

Key decisions and trade-offs

  • Prefect + Kubernetes: Chosen over Step Functions + SQS for a better built-in UI, lower cost and less build effort.
  • Swappable execution layer: A Step Functions + SQS fallback sits behind an adapter, so changing runtimes means changing one adapter.
  • Pod-level isolation: Each run has its own memory limits, so one heavy tenant can’t slow down the others.

Challenges

  • Serving 3 teams with different needs from one platform
  • Integrating existing legacy Python frameworks
  • Building logging, metrics, infrastructure, notifications and failure strategy from scratch

My role

Co-designed the architecture with the lead engineer, authored the HLD/LLD, and guided 2 engineers through implementation.

Results

  • Tenant A: 60h → 12h
  • Tenant B: 20h → 2h
  • Tenant C: 18h → 7h
  • Tenant D: 9h → 2h
  • Tenant E: 4h → 40m

Tech: Prefect, Kubernetes (EKS), Redis, Python, AWS

Dashboard Performance Overhaul

Enterprise AI SaaS · Customer-facing dashboards used by client leadership teams

The problem

Dashboards took around 20 seconds to load. Causes stacked up: unoptimized jobs, database load spikes, queries getting killed, and no proper caching.

What was built

Optimized MongoDB queries and used projections to fetch only the fields needed. Refactored 2 microservices into modular components, added a caching layer with cache on/off control built into the UI, and moved services from uWSGI to AWS Fargate.

Key decisions and trade-offs

  • Projections first: Fetch only the fields each widget needs, instead of whole documents.
  • Controllable caching: A caching layer with an on/off control built into the UI, so fresh data is one click away.
  • Modular services: Two heavy services split into modular components that scale on their own.

Challenges

  • Several causes of slowness at once: jobs, queries and caching
  • Keeping data fresh while caching aggressively
  • Refactoring live, customer-facing services without downtime

My role

Led the investigation and the fix: query optimization, service refactor, caching design and the move to AWS Fargate.

Results

  • Load time cut from about 20 seconds to under 2 seconds (90% faster)
  • Fewer database spikes and killed queries
  • Services now scale independently on AWS Fargate

Tech: MongoDB, Django, AWS Fargate, Caching

Hotel Reviews Aggregator

B2B travel platform

The problem

Hotel reviews came from 3 global suppliers, each with its own format and API rate limits.

What was built

A Python service that pulls reviews from every supplier and converts them into one common schema using pluggable adapters. Ingestion jobs respect each supplier’s rate limits, and all reviews are segregated and ranked in Elasticsearch.

Key decisions and trade-offs

  • Adapter pattern: One adapter per supplier, so adding a new supplier takes minimal code changes.
  • Rate-limit-aware jobs: Ingestion paced per supplier, so no API limits are breached.
  • Elasticsearch: Reviews segregated and ranked for fast, relevant results on hotel pages.

Challenges

  • A different data format from every supplier
  • Strict API rate limits during ingestion
  • Ranking a very large review set quickly

My role

Designed and built the aggregator service, its adapters and the Elasticsearch ranking.

Results

  • 1M+ reviews unified in one schema
  • Ranked and searchable through Elasticsearch
  • New suppliers can be added with minimal code changes

Tech: Python, Elasticsearch, Adapter pattern

Secure Bank Payout Integration

Warranty & assurance platform

The problem

Cashback on warranty and assurance products had to reach sellers and retailers through the apps of major consumer brands. Payouts needed to be secure, reliable and traceable.

What was built

An integration with a major bank’s payout APIs, with encryption using certificates and public/private key cryptography stored securely on the server, exponential backoff retries for failed calls, a daily reconciliation job to match every payout, and live monitoring.

Key decisions and trade-offs

  • Certificate-based encryption: Public/private key cryptography, with keys stored securely on the server.
  • Exponential backoff: Failed calls retried with growing gaps, so temporary bank issues don’t lose payouts.
  • Daily reconciliation: A job that matches every payout each day, so nothing goes unaccounted.

Challenges

  • Handling bank-grade encryption and key management
  • Recovering from temporary bank API failures
  • Proving every payout landed

My role

Built the bank integration, its encryption, retry logic and the daily reconciliation job.

Results

  • 10,000+ encrypted payouts every month
  • Faster settlement and higher success rates
  • More trust from partners and retailers

Tech: Django, Cryptography, Retries, Reconciliation
